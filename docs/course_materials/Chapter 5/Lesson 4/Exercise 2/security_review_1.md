Security Audit — Advanced Task Search (GET /workspaces/:workspaceId/tasks/search)
Scope: git diff HEAD across src/routes/tasks.ts, src/services/taskService.ts, src/app.ts, prisma/schema.prisma, plus new files src/middleware/requireWorkspaceMember.ts, src/middleware/rateLimit.ts, src/utils/taskSearchCursor.ts, tests/taskSearch.test.ts, and the new migration.
Verdict: NOT APPROVED. The endpoint's internal defenses (SQLi, tenant scoping, cursor validation) held up under attack. The audit nevertheless breaks the system twice — once at the feature boundary and once in production-readiness — and finds that the headline performance claim of the diff is false.

Area 1 — SQL Injection: defense held
I attempted injection through every dynamic surface. All failed, for the right reasons:
- sortBy/sortOrder (src/routes/tasks.ts:209-213): both pass through z.enum(TASK_SEARCH_SORT_BY/TASK_SEARCH_SORT_ORDER) and then enter SQL only via the server-side allowlist SORT_EXPR table (src/services/taskService.ts:344-374) and the server-literal dirSql. sortBy=createdAt; DROP TABLE tasks dies at Zod with a 400 before any DB access. No client string ever reaches SQL text — this is the correct pattern.
- Cursor values (src/utils/taskSearchCursor.ts:66-113): base64url → JSON → strict Zod with per-sortBy type narrowing (::real rank ∈ 0,2, ::int int4 range, ISO timestamps, uuid id). My tamper attempt (v: "DROP TABLE tasks; --") is rejected at the ISO check, matching the regression test at tests/taskSearch.test.ts:476-491. In SQL, cursor values are always bound parameters with explicit casts (${cursor.v}::timestamptz, ${cursor.id}::uuid).
- Everything else is a bound parameter: q, workspaceId, assigneeId, status/priority (ANY($n::text[])), projectIds (= ANY($n::uuid[])), LIMIT ${limit + 1}. The ±infinity sentinels are constant SQL, not client text.
- Nit: Buffer.from(token, "base64url") silently discards invalid characters instead of throwing — downstream Zod still rejects, so the outcome is a 400. Acceptable.
One process control to add: the injection safety rests entirely on every future SORT_EXPR/CURSOR_PROJ_EXPR entry being a server literal. A CI grep gate (no Prisma.sql template containing interpolated client strings) would make that durable.
Area 2 — Broken Access Control: endpoint internally sound, system-level bypass found
Within the endpoint, I could not bypass the membership check:
- Chain is correctly ordered: authenticate → requireWorkspaceMember → rateLimiter → Zod → DB (src/routes/tasks.ts:226-231). requireWorkspaceMember looks up the compound unique (userId, workspaceId) and returns identical 404s for "missing workspace" and "not a member" — no enumeration oracle. The workspaceId predicate p.workspace_id = $1 is inside the same WHERE as the keyset condition, so cursor pages cannot escape scope.
- assigneeId=<foreign uuid> merely narrows inside the scoped query → empty result, no leak (verified by test E13). me resolves post-auth and can't be spoofed. projectId is pre-validated against the workspace and is also double-protected by the join predicate. The assignee-name embed is membership-gated (A1 fix, the EXISTS (workspace_members…) subquery).
CRITICAL — Finding #1: I don't need to bypass it. The diff edits src/routes/tasks.ts, imports authenticate at line 14… and wires it into exactly one route. Every sibling route on the same router is wide open (taskRouter.get("/"), line 72; GET /:id, PATCH /:id, POST /, comments at POST /:taskId/comments). src/app.ts:41 mounts it with no auth. Concretely, as a fully anonymous attacker:
GET /tasks?q=invoice          → full-text search across ALL tenants' tasks
GET /tasks/<any-uuid>         → any task + comments
PATCH /tasks/<any-uuid>       → modify any task
listTasks (src/services/taskService.ts:148-171) runs the same search_vector FTS with no workspace scoping whatsoever. The new endpoint's carefully structural tenant model is bypassed by walking one directory up. "Can I see tasks from a workspace I don't belong to?" — yes, all of them, without a token. This is technically pre-existing, but it's a missing guard in the exact file this diff touches, and it's rate-limit-free, unlike the new endpoint.
CRITICAL — Finding #2: the token check does not exist. src/middleware/authenticate.ts is a stub returning 501 Authentication not implemented. Direct answer to the brief's question 3: there is no SAML/JWT verification to bypass — there's nothing. Today the endpoint fails closed (501 for everyone, feature dead-on-arrival). The tests vi.mock it with a fake that unconditionally trusts authState.userId (tests/taskSearch.test.ts:72-87), so the entire 401/404 security contract of this feature is validated against a mock, not reality. One naive "fix" (call next() without verifying, per the TODO comment's shape) converts the endpoint to fully anonymous. Every guarantee in this audit is conditional on a correct authenticate landing.
LOW: the cursor token is unsigned and carries no workspaceId — a member of two workspaces can replay/forge cursors cross-workspace. The SQL scope still fences the data (I verified the keyset predicate is AND-ed into the scoped WHERE), so this is pagination-state confusion, not a leak. Recommend HMACing the cursor with the server secret and embedding the workspace id.
Area 3 — Input Validation / DoS: no crashes found; real resource-exhaustion paths exist
What I threw at it that failed to break it (all correct):
- limit=0|101|-7|banana|1e9 → 400 (Zod int 1–100, default 25; over-fetch is +1). No unbounded fetch.
- Garbage cursors (!!!!, truncated base64, unknown keys, type-confused v, out-of-range ranks/dates) → 400, never 500 — the codec's strict Zod (E9) plus range guards (C1) hold, including the timestamptz-range guard against year -271821.
- Operator junk (q=& "or"), stopword-only q (the of and), whitespace q → 200, reduced to "no search" via the numnode preflight — no 500 path, no ReDoS (no user-controlled regex anywhere; renderSnippet uses replace chains).
- A corrupt cursor never reaches SQL; JSON.parse failures are caught.
What actually works as an attack (against an authenticated member, which the rate limit permits at 60/min):
- q has no length cap (z.string().optional(), src/routes/tasks.ts:202); cursor likewise. express.json({limit:"1mb"}) is irrelevant — these arrive via the query string of a GET. Only Node's ~16KB request-line cap bounds them. Each request then evaluates websearch_to_tsquery('english', $q) (not constant-folded with a bound parameter) per matched row, at up to three sites per row (@@ filter, ts_rank in ORDER BY/keyset, ts_headline). A ~2000-distinct-term q matching a broad GIN posting list multiplies hard. No statement_timeout is configured (src/utils/prisma.ts — bare client) — even though the project's own ADR names it as the backstop. That's a sustained CPU-exhaustion vector with one account.
- Postgres's internal tsquery size limits turn extreme q into a thrown error → generic 500, not a 400; minor availability nit.
- Rate limiter (src/middleware/rateLimit.ts): (a) in-process Map — trivially bypassed the moment a second instance exists (the comment admits this); (b) fixed window → 2× burst at boundaries; (c) hits entries are filtered on read but keys are never evicted — every user who ever searched leaves a permanent entry; slow unbounded growth; (d) req.ip ?? "anonymous" fallback only matters if mounted pre-auth (it isn't). Note the limiter protects only the new endpoint — the unauthenticated GET /tasks?q= from Finding #1 has no rate limit at all.
Area 4 — Performance at 1M rows: the diff's central performance claim is false
HIGH — Finding #3: the two new indexes are dead weight for the query they were built for. The migration adds tasks(project_id, created_at DESC, id ASC) and (project_id, updated_at DESC, id ASC), with a comment promising "each page is an index-range scan of O(limit)". But the search scopes via JOIN projects p … WHERE p.workspace_id = $1 (src/services/taskService.ts:672-679) — in the default path no equality predicate on t.project_id exists, so an index whose leading column is project_id can be used neither for the filter nor for the ORDER BY:
- A nested loop per project (driving from projects.workspace_id) cannot produce the global created_at DESC, id ASC order — Postgres won't merge-append parameterized scans — so the planner falls back to Seq Scan + top-N sort.
- Bitmap-OR across the workspace's projects discards ordering → same fallback.
And there is no index with created_at as a leading column anywhere in the schema — old or new. The keyset predicate t.created_at < $cur AND t.id > $cur_id is therefore equally unindexable. Net effect: the default search (GET .../tasks/search, no filters) is a full-table Seq Scan plus a sort of the whole join-filtered slice, on every page, forever. At 1M rows that's ~1M heap tuples read per request, 60 times per minute per user. The indexes only pay off in the narrow case of exactly one projectId filter — a case the UI may never exercise as default. The fix the project's own ADR already sketches: denormalize workspace_id onto tasks (trigger) + (workspace_id, created_at DESC, id ASC) / (workspace_id, updated_at DESC, id ASC) — then each keyset page is a true range scan.
Same class of problem, other sort keys: dueDate (COALESCE(..., ±infinity)), priority (the CASE rank), and title have zero index support — every page is a scan + sort of the workspace slice. At 100k+ tasks per workspace that's a six-figure sort per request. The CASE-based priority is fine for correctness (and the E12 ELSE 0 handling is good), but the documented escape hatch (generated priority_rank column + composite index) is unimplemented.
HIGH — Finding #4: the relevance path's GIN index is global, not tenant-local. t.search_vector @@ websearch_to_tsquery(...) has no workspace prefix; a broad-but-legal stem (e.g., matching "test") builds a GIN bitmap across all tenants' matches — potentially most of the 1M-row table — then computes ts_rank for every match, then sorts, and only then does the join filter workspaces. The ADR's own mitigation ladder (btree_gin (project_id, search_vector), or trigger-copied workspace_id + GIN (workspace_id, search_vector)) is documented but not built, and there's no statement_timeout backstop. This is the single most expensive query shape in the feature and it degrades precisely as the table grows.
Genuinely good perf decisions worth keeping: OFFSET-free keyset, the page CTE that confines ts_headline and relation embeds to ≤101 rows, no COUNT(*), and the stopword preflight that avoids forfeiting the GIN index with an OR-guard.
LOW (operational): the migration uses plain CREATE INDEX (locking) — and the CI diff now runs npx prisma migrate deploy. On a 1M-row production table that build holds a lock for the duration; at scale it needs CONCURRENTLY (which means breaking out of Prisma's transactional migration).
Diff-specific mandates
- Missing guards: found — the authenticate import exists in tasks.ts but guards only the new route (Finding #1). Within the new logic path itself, no guard is missing: membership runs before any DB touch in every branch, including the me-sentinel 401 branch and the cursor-mismatch 400 branch.
- Insecure defaults: found — default sort (createdAt desc) is precisely the sort with no supporting index (Finding #3), turning the endpoint's most common request into the worst query. Data-leak defaults: none; 404-uniformity, snippet escaping, and the assignee-name membership gate are all correctly defaulted.
- Unintended side-effects: none. The taskService.ts diff is a pure append after toTaskDetails; listTasks/getTask/updateTask byte-identical; the express.d.ts change is additive; /workspaces router is empty so the new mount at /workspaces/:workspaceId/tasks cannot be shadowed; CI changes are additive (real-DB test layer, migrate deploy).
Required remediations before merge
1. Ship authenticate (JWT verification per the stub's TODO) — or explicitly gate the endpoint behind a feature flag. As it stands the feature is either dead (501) or unguarded-by-illusion.
2. Put auth + tenant scoping on the legacy /tasks router (or block it). A workspace-scoped, authenticated search endpoint is meaningless next to an open cross-tenant FTS endpoint in the same file.
3. Index the actual access path: denormalized tasks.workspace_id + (workspace_id, created_at DESC, id ASC) and (workspace_id, updated_at DESC, id ASC); drop or re-justify the (project_id, …) composites (they serve only single-project filtered pages); plan the tenant-local GIN ladder for relevance.
4. Set a statement_timeout (client-level or role-level) and cap q/cursor length (e.g. .max(256) for q, .max(1024) for cursor); convert rate-limiting to a shared store before any multi-instance deployment and evict idle keys.
The endpoint itself is one of the better-hardened pieces of this codebase — parameterization, cursor validation, and tenant scoping all survived a genuine attempt to break them. It is the boundary around it that fails: an auth stub at the gate, an open door one floor down, and indexes that point away from the query they were named for.
